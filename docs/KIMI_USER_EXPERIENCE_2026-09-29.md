# K3 用户体验实测：2026-09-29

## 结论

元衡默认 Kimi 分组的 14 条合成请求均完成 HTTP 200、正确内容或工具调用，并有正常结束标志。这不是全量 KVV 通过：用量字段仍有缺失，长尾等待也实际存在。

- 13 条请求要求返回 usage，另 1 条明确关闭 usage。前 13 条中，4 条没有思考 Token 计数，5 条没有缓存读取计数；这两组可能重叠。
- 真实缓存命中已验证：同渠道重复输入 5,720 Token，第二次报告全部命中，消费日志也计入 5,720 缓存 Token。
- 普通分组会选择不同渠道，字段形状随请求变化。不能把缺字段解释成缓存未命中、缓存过期或没有思考，也不能只凭渠道变化断定缓存池不共享。
- 本地兼容补充 `cache_read_tokens` 后备来源，并使用实际 usage 切片回归。完全没有计数来源的响应仍保持未知；不从思考正文长度推算用量。
- 线上仍为 `main-18a2e98`；本地兼容没有提交、部署或用于这 14 次在线调用。

## 范围与方法

- 用户授权使用元衡测试令牌、按用户体验实测、费用不设上限；实际采用有限的串行样例，不做压测。
- 入口：`nan.meta-api.vip`，`/v1/chat/completions`，模型 `kimi-k3`，令牌默认分组 `Kimi · 优质（第三方）`。
- 在线请求时段：北京时间 2026-09-29 21:37 至 21:44；日志及额度核对截至 21:49。
- 只发送合成问题、随机前缀目录、演示库存工具数据，不上传 Mac 文件、真实用户正文或个人信息。
- 客户端不自动重试、换入口或指定渠道；没有修改线上分组、渠道、账户或重试设置。服务端内部重试次数未取得完整证据，不宣称为零。
- 同时收集原始 JSON/SSE 的 usage、内容/思考/工具首包时间、结束标志，再按本站 `x-oneapi-request-id` 精确匹配日志。上游的 `x-request-id` 不能替代本站请求编号。
- 在线模型请求全部停止后，才运行会占用本机 CPU 的 Go 回归，避免混入本地构建负载。

## 字段来源与诊断边界

### 1. 缓存确实能够命中

长前缀首次与重复 1 都在渠道 1466，输入均为 5,720 Token：

```json
{"prompt_tokens":5720,"completion_tokens":57,"total_tokens":5777,
 "completion_tokens_details":{"reasoning_tokens":41},
 "prompt_tokens_details":{},"cache_write_tokens":0,"cache_read_tokens":0}
```

```json
{"prompt_tokens":5720,"completion_tokens":73,"total_tokens":5793,
 "cached_tokens":5720,"completion_tokens_details":{"reasoning_tokens":56},
 "prompt_tokens_details":{"cached_tokens":5720},
 "cache_write_tokens":0,"cache_read_tokens":5720}
```

第二条日志 `cache_tokens=5720`，扣费也使用缓存比例。首次的明确零和第二次的命中不是同一个断言。样本没有设置跨分钟等待，无法据此测出缓存 TTL；也没有证据说明命中一定更快。

### 2. 有思考内容，但缺少思考计量

渠道 1468 的 4 条要求 usage 的思考请求均有 `reasoning_content`，但没有任何受支持的 `reasoning_tokens` 位置。流式例子：

```json
{"prompt_tokens":119,"completion_tokens":525,"total_tokens":644,
 "prompt_tokens_details":{"cached_tokens":64}}
```

本地兼容可以补平铺缓存别名，不能从该响应恢复真实思考 Token 数。这里只定位到“元衡客户端边界缺少字段”，没有取得供应商原始入站响应，因此不能断言供应商漏报或元衡中间层丢失。

### 3. 缓存未知不能补零

渠道 1402 的长前缀重复请求报告输入 5,720、输出 32、思考 18，但没有缓存计数来源。渠道 1411 的另一条工具回环也未报告缓存量。分别记录未知，不能因为其他请求命中过而继承其缓存状态。

### 4. 实际等待较长

本轮最慢的 high 请求在约 23.3 秒出现思考片段、约 40.7 秒出现正文；auto 工具请求约 30.6 秒出现思考片段、约 32.0 秒出现工具参数。计时包括本机到元衡的网络以及完整处理链路；无法单独据此归因 CPU、供应商排队或网络。

没有测试并发、P99、稳定输出速率、长上下文性能、图像/视频、192 MiB、完整官方 KVV 或假成功退款。不报告这些项目通过，也不将普通 API 成功等同于上线验收通过。

## 本地修复与回放

- 复用已有 K3/OpenAI兼容与 Moonshot 原生 Chat 归一逻辑，不修改共享 DTO 或其他模型。
- `cache_read_tokens` 作为最低优先级后备来源；标准嵌套字段、已有别名及单 choice 证据仍优先。
- 明确 0 合法；负数、非整数、溢出、超过明确输入总量的后备值不用于补齐。`cache_write_tokens` 不当作读取缓存，不重复增加总量或收费。
- 先新增真实 usage 切片回归，确认 `reported_cache_zero/stream=false/force=false` 在补丁前失败，再补上后备来源。
- 回放只重建包含实际 usage 的 JSON/SSE 夹具，不重放供应商服务，也不把回放通过写成补丁线上实测通过。
- 定向 handler/隔离 SQLite 结算回归通过；实际 usage 切片覆盖 16 个 JSON/SSE/强制格式化组合，结算覆盖 6 种字段形状的流式/非流式。
- 全仓 `go test -p 2 -timeout 120s ./...` 通过；controller 与 OpenAI handler 的 Kimi、流式、失败退款定向 `-race` 重复 2 次通过。
- `go build -p 2 ./...`、`make verify-notes`、`git diff --check` 通过；本轮测试会话全部退出，末次进程检查未发现 Go 构建或测试遗留进程，本轮遗留测试进程为 0。
